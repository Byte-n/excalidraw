# 文档分层与维护规范

约束 ADR、业务规格（spec）、phase 计划与执行账本的编写、变更和维护。模板见 `docs/adr/_template.md` 与 `docs/spec/_template.md`；phase 计划与账本模板见 `.agents/skills/phase-workflow/assets/`。

## 目录

- [业务规格](spec/README.md)：系统当前有效行为，按领域组织。
- [架构决策](adr/README.md)：长期决策、取舍与取代关系。
- [实施计划](plan/README.md)：phase 范围、执行账本与恢复入口。
- [设计工作区](design/)：提案与调研，不作为长期事实源。
- [待办清单](TODO.md)：跨 phase 的待办事项，不是长期事实源。
- `lark-exmples/`：只读样例与映射数据，不参与本文档规范，禁止修改。

## 1. 分层与事实源

| 层 | 位置 | 回答的问题 | 形态 |
| --- | --- | --- | --- |
| 入口 | `AGENTS.md`、`docs/README.md` | 先读什么、边界在哪 | 索引与维护规范 |
| 约束 | `AGENTS.md`、`.agents/skills/*` | 这类改动怎么做 | 规则与流程 |
| 现状 | `docs/spec/*.md` | 系统现在是什么 | 按领域，覆盖式更新 |
| 决策 | `docs/adr/*.md` | 为什么长期这样定、代价是什么 | 按主题，不可变 |
| 执行 | `docs/plan/*.md`、`docs/plan/progress/*` | 这次做什么、做到哪 | 一次性，完成后冻结 |
| 工作区 | `docs/design/*` | 尚未定案的提案与调研 | 可改写，定案后提炼 |

不设 PRD。需求范围与迭代记录由 phase 计划的“背景与目标”、执行账本和 ADR 的“后果”承担；跨 phase 的主题在 `docs/plan/README.md` 索引中追踪。`docs/design/` 只作为提案与调研工作区，不作为长期事实源；定案后提炼 ADR、更新 spec，并归档或删除设计稿。

冲突顺序：代码与测试 > `docs/spec/` > `docs/adr/` > `docs/plan/` > `docs/design/`。发现冲突时必须停止当前动作并报告，不得静默选择。

## 2. 通用规则

- 以 `_` 开头的文件是模板，不属于事实源，不纳入任何索引。
- 一个事实只有一个家：ADR 写理由与约束，spec 写当前行为，phase 写范围与执行；不得互相复制。
- 文档必须可验证：spec 的规则要能被代码或测试验证；ADR 要写“如何确认”；phase 要写验证要求。
- 文档与行为变更同一提交：不允许先改代码，之后再补“文档提交”。
- ADR 与 spec 的最终文本由 mainAgent 定稿；subagent 只能提出变更影响与候选决策，不得直接定稿。
- 不写历史：spec 只写当前有效行为；phase 完成后冻结；ADR 不可改写，只能被取代。
- 不引入 PRD 或第五层文档；`docs/design/` 定案后不再长期维护。
- `docs/lark-exmples/` 是只读样例数据，不得作为事实源或修改其中的相对链接。

## 3. ADR

### 3.1 准入

满足任意两条才写：难逆转、跨模块或跨服务、约束未来实现、有真实取舍。局部重构、命名、UI 细节、一次性任务不写。一个主题一篇，不是每个任务一篇。

### 3.2 命名与生命周期

- 路径 `docs/adr/NNNN-kebab-case.md`，四位编号，不复用。
- 状态：`提议 / 已采纳 / 已放弃 / 已取代`；只有“已采纳”具有约束力。
- 已采纳后正文不再改写；只允许更新状态、关联链接和明显笔误。
- 被取代时：旧 ADR 改为“已取代”并写 `被取代：ADR-NNNN`；新 ADR 写 `取代：ADR-NNNN`。两篇都保留。
- 索引 `docs/adr/README.md` 与 ADR 同一提交更新；不得存在未入索引的 ADR。
- 模板：`docs/adr/_template.md`。

### 3.3 何时创建

- 实施前：phase 依赖一个未定决策时，先写“提议”ADR；确认后改“已采纳”，再进入计划。
- 实施中：新冒出来的决策先记在计划或账本，收口时升格为 ADR；不要边写代码边改 ADR 正文。
- 实施后：只维护索引和取代链。每次触及该领域或每季度检查一次失效 ADR。

### 3.4 反模式

- 每个任务一篇 ADR，或把 spec 的行为规则复制进 ADR。
- 没有“如何确认”的 ADR，或采纳后继续改写决策正文。
- 用 ADR 记录实施步骤、进度和任务拆分。

## 4. Spec

### 4.1 范围与结构

- 一个领域一份 spec，描述当前有效行为；不能用一个文件混合多个领域。
- 模板：`docs/spec/_template.md`。
- 元数据固定写：状态、最近核对、适用域、关联 ADR。
- `最近核对` 只在逐条对照代码或测试核对后填写日期；仅补元数据或改措辞时保持 `待核对`。

### 4.2 写作规则

- 用业务语言描述功能流程、契约、规则与不变量；不写文件路径、类/函数/变量名、表名、库与版本、配置项、端口、代码片段、具体实现参数。
- 一个需求只写一个可观察行为；出现多个“并且”时拆成多条。
- 用 `必须 / 不得` 表达硬约束，强度等价于 `SHALL / MUST NOT`；`可以` 只用于真正可选的规则。
- `场景`（给定 / 当 / 则）只用于 P0 不变量、权限边界、协作协议和对外契约；普通规则不必每条都写。
- 每条规则必须能被代码或测试验证；不能验证的放 ADR 或 TODO。
- 显式写“边界与非目标”“假设与开放问题”，避免 agent 自行补全。
- 只写当前有效行为；不写“以前 / 现在 / 未来”，不写移除说明。

### 4.3 更新与维护

- 行为变化时，spec 与代码、测试同一提交更新；没有 spec 变更的代码变更要在任务报告中说明“无规格影响”。
- 一个 phase 内多个任务改同一份 spec 时，各任务只改自己负责的章节；收口时统一核对，避免互相覆盖。
- 规格变更以 `规格影响` 形式进 phase 计划；收口时合并，不依赖 agent 记忆。
- 拆分、合并或删除 spec 时，同步更新 `docs/spec/README.md` 的索引。

### 4.4 反模式

- 把 feature spec 的用户故事、优先级、成功标准写进领域 spec。
- 把 design 的架构、数据模型、接口选型写进 spec。
- 给每条规则编号，或把每条规则都写成 GIVEN / WHEN / THEN。
- 在 spec 里保留历史演进、旧方案对比或“待迁移”说明。

## 5. Phase

### 5.1 计划

- 计划头部固定写：状态（未开始 / 进行中 / 已完成 / 已取消）、关联 ADR、规格影响。
- 计划必须包含 `## 规格与决策影响`，列出预期规格变更、需要新建或取代的 ADR，以及只在本期有效的局部决策。
- 计划中的架构决策是临时记录：实施前能定案的先写 ADR；实施中产生的在收口时归类到 ADR、spec、TODO 或丢弃。
- 计划只写范围、架构设计、任务边界、依赖与验收；不写执行过程和历史方案。
- 新增计划路径 `docs/plan/phase-<编号>-<slug>.md`；存量无账本计划保留原文件名，在 `docs/plan/README.md` 标注“存量计划（无账本）”。

### 5.2 执行

- mainAgent 负责调度、验收与提交；不参与具体开发。需要代码审查时另起独立 subAgent。
- subAgent 负责实现与自验证，报告必须含：实际变更、验证结果、规格影响（无 / 章节列表）、ADR 候选（有 / 无）、遗留问题、建议提交信息。
- 验收通过后立即提交，一个任务一个提交；账本随任务更新，不批量补提交。
- 代码任务按受影响包执行 `yarn workspace <pkg> test` 与 `yarn workspace <pkg> typecheck`；跨包逐个执行。

### 5.3 收口

- 计划内每个架构决策必须有去向：ADR、spec、TODO 或丢弃；写入账本 `## 决策去向`。
- 规格与代码同一提交；ADR 索引、计划索引、`TODO.md` 与相关文档同步更新。
- 计划状态改为 `已完成` 或 `已取消` 并冻结；账本记录最终 HEAD、验证结果与遗留限制，永久保留。

## 6. 新增与迁移

- 新增或重写 spec 直接从 `docs/spec/_template.md` 复制，不再按旧文件补元数据。
- 领域拆分或合并时，同步更新 `docs/spec/README.md` 的索引与交叉链接。
- 现有 phase 计划补状态、关联 ADR 与规格影响；没有执行账本的在 `docs/plan/README.md` 标为存量计划，不补造账本。
- 现有设计稿保留为工作区；已定案内容提炼为一篇主题 ADR，不按条目批量拆分。
- 不重写历史计划，不补造执行证据。
- `docs/sequence-diagram/` 为受 `docs/lark-exmples/` 只读相对链接约束的存量计划，暂留原路径；迁移时需同步处理该只读链接。

## 7. 维护节奏

- 每个任务：subagent 报告规格影响与 ADR 候选；mainAgent 验收时检查 spec 是否同提交更新。
- 每个 phase：执行收口清单，合并规格变更，提炼 ADR，更新索引，冻结计划。
- 每季度或每次触及领域：检查 ADR 状态与取代链、spec 的 `最近核对`、计划索引和失效链接。
- 可选自动化：在 pre-commit 或 CI 中检查 ADR 元数据、索引一致性、spec 元数据、phase 必需段落和 Markdown 内链；不做定时全量重写。

## 8. 检查清单

- [ ] 新决策有 ADR，状态、索引与取代链正确。
- [ ] 已采纳 ADR 的正文未被改写。
- [ ] spec 与代码、测试同一提交。
- [ ] 新增规则可被代码或测试验证。
- [ ] phase 计划有规格影响，账本有决策去向。
- [ ] ADR 索引、计划索引与正文链接有效。
- [ ] 没有把 feature spec 或 design 内容写进领域 spec。
