# 复合图形数据结构总纲

## 目标与依据

本方案为 Excalidraw 增加可扩展的复合图形模型，最终支持 [lark-examples-data.json](lark-examples-data.json) 中的图形及其可编辑行为。样本包含 11 种顶层元素类别；其中 74 个 `composite_shape` 实例使用 64 种子类型。样本只能证明已出现的字段和取值，不能代替原平台的完整图形与控制点规格。

分期交付以 [第一期：现有图形的新数据结构](phase-1.md) 开始，随后进入 [第二期：形状职责收敛与思维导图结构统一](phase-2.md) 和 [第三期：Lark 复合图形逐项实现](phase-3.md)。第一期只允许声明已实现的矩形、菱形、椭圆；第二期统一思维导图形状的数据外形，并收紧 `type` 与 `shape` 的职责。以后每实现一种图形，才增加对应的类型分支、参数校验、几何和测试。总纲中的未来能力不表示当前期要预先声明其类型。

## 元素类别与图形种类

画布元素的顶层 `type` 表示元素的交互和数据归属，复合图形内部的 `shape.id` 表示外观种类。

| 元素类别 | 长期数据归属 | 原因 |
| --- | --- | --- |
| 普通预设图形 | `type: "composite_shape"` | 共用位置、样式和图形编辑框架，由 `shape.id` 选择几何与控制点 |
| 现有线条、箭头、文字、图片、画框 | 保留现有元素类别 | 具有独立的路径、文字或资源语义 |
| 外部 `connector`、`text_shape` | 在对应功能期适配现有线条/箭头、文字模型 | 保留端点、箭头样式和文字属性 |
| 外部 `mind_map` | 保留现有 `mindmap-node`、`mindmap-edge` 语义 | 父子关系、自动布局和折叠是节点行为；节点外观使用独立的 `MindmapShapeData`，可复用图形几何但不改变节点身份 |
| 外部 `table`、`table_er`、`table_uml`、`combined_fragment` | 对应功能期建立表格类语义模型 | 行列、合并单元格和标题需要结构化数据 |
| 外部 `life_line`、`activation`、`section` | 对应功能期决定专用语义模型 | 序列图与分区行为不能仅靠图形轮廓表达 |

原平台的 `composite_shape.type` 是导入格式的子类型字段，映射到内部的 `shape.id`。外部 ID 不因名称相近而自动合并；例如 `rect` 与现有 `rectangle`、`round_rect` 与 `round_rect2` 是否等价，需要逐项验证几何和控制点后再决定。第一期不导入这些外部子类型。

## 持久化契约

复合图形沿用 `_ExcalidrawElementBase` 的 `id`、`x`、`y`、`width`、`height`、`angle`、样式、分组、绑定、排序和协作字段。新增的形状信息放在正式元素字段中，不放入 `customData`。

```ts
type ExcalidrawCompositeShapeElement = _ExcalidrawElementBase &
  Readonly<{
    type: "composite_shape";
    shape: ShapeData;
  }>;
```

`ShapeData` 必须是以 `id` 判别的联合类型。无专属参数的形状只保存 `id` 和 `schemaVersion`；有专属参数的形状以与 `id` 同名的键保存数据，即 `shape[shape.id]`。该键的字段和单位由相应图形的规格规定，不能使用无约束的 `Record<string, any>` 代替已实现图形的类型。

每种形状的校验必须保证：

- `shape.id` 是当前版本实际支持的图形；未知 ID 不得静默渲染为其他图形。
- `shape.schemaVersion` 对应此 ID 的参数结构；缺失或不支持的版本必须报错。
- 有参数时，只有与 `id` 同名的专属数据可作为该形状的来源；无参数时不强加空对象。
- 数值有限、坐标系和单位明确，参数满足该形状的几何约束。
- 同一元素只保存必要的来源数据；可由参数计算的路径、控制点和命中区域不重复持久化。

## 三种版本的职责

| 字段 | 含义 | 变化时机 |
| --- | --- | --- |
| 元素 `version`、`versionNonce` | 单个元素的修订与协作协调 | 元素发生编辑时，沿用现有机制 |
| `shape.schemaVersion` | 当前 `shape.id` 的参数结构版本 | 该形状的持久化参数结构升级时 |
| 文件顶层 `version` | 整份 Excalidraw 文件的格式版本 | 文件格式发生不兼容变化时 |

拖动图形控制点更新该形状的专属数据和元素修订号，不更新 `shape.schemaVersion`。第一期的三种图形均从 `schemaVersion: 1` 开始。

## 图形定义与编辑行为

持久化数据只描述状态，图形定义代码负责行为。长期模型中，每个已实现的 `shape.id` 应有一份可注册的定义，提供参数校验、默认值、局部几何、控制点、控制点拖动更新、文字区域等能力。几何结果须能用于画布和 SVG 绘制、命中检测、填充、箭头连接边界及导出，避免各模块解释同一图形时出现不同轮廓。

后续实现可调图形时，几何接口需要允许多段描边、多个填充轮廓和内孔。控制点由形状参数及当前尺寸推导；若控制点位置本身决定几何，例如样本中的 `cube.control_point`，它是该形状的专属参数。行为代码和临时拖拽状态不得写入场景 JSON。

第一期只让现有三种几何行为通过新的数据结构工作，不建立尚未使用的控制点参数或占位图形定义。

## 文字与语义元素

普通图形的绑定文字继续是独立的 `text` 元素，以 `containerId` 指向复合图形。思维导图节点仍通过 `graphId`、`role`、`parentId` 和 `order` 表示结构；第二期将其 `shape` 改为独立的 `{ id, schemaVersion }` 结构，允许复用几何定义但不得因此丢失节点身份。表格单元格及其他语义内容在各自功能期建立正式结构，不塞入复合图形的专属参数。

`lark-examples-data.json` 中嵌入的文字、翻转、主题色和富文本样式需要独立的导入映射及能力验收；第一期不假定现有文字和样式类型已经覆盖这些字段。

## 版本与分期

新模型改变现有矩形、菱形、椭圆的元素判别方式。这是破坏式大版本：不迁移或兼容旧场景、旧库及旧客户端。新建和保存只生成规范结构；协作使用当前大版本的数据结构。

总体顺序如下：

1. 第一期：将现有三种基础图形改为新数据结构，保持它们的现有可见与可编辑行为。
2. 第二期：将思维导图形状改为对象结构，并清理 `type` 与 `shape` 的混用判断。
3. 后续图形期：逐个加入已实现的外部子类型及其参数、几何、控制点和导入映射；不提前扩展联合类型。
4. 后续语义元素期：按功能处理外部连接线、表格、序列图元素、分区等；复用已有 Excalidraw 能力时保留其语义。
5. 完整互通期：验证 `lark-examples-data.json` 的所有元素、样式与行为；是否要求再导出为原平台格式须在该期确定。

每期结束时，已声明的类型都必须能创建或导入、编辑、保存重开、命中和导出。不能仅添加 TypeScript 字符串联合或静态预览就视为实现。

## 需要持续核对的边界

- 原平台样本不是完整规格；未在样本出现的默认参数、控制点规则和缩放行为要从实际产品或正式格式定义核对。
- 新文件、库项目和剪贴板均可能包含元素数据；入口必须校验结构并拒绝旧格式。
- 图形渲染、几何命中、箭头绑定、文字绑定、复制和协作需要使用同一规范元素结构。
- 对尚未支持的外部形状应保留明确的导入错误或占位策略，不能静默丢失，也不能伪装成已实现的形状。
